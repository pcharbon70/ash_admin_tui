**Designing a Terminal UI for AshAdmin with TermUI**

**Overview of AshAdmin Web UI**

**AshAdmin** is the "super-admin" web interface for managing Ash framework resources, built as a Phoenix LiveView application[preview.hex.pm](https://preview.hex.pm/preview/ash_admin/0.9.3/show/README.md#:~:text=An%20admin%20UI%20for%20Ash,Built%20with%20Phoenix%20LiveView). It automatically provides CRUD pages for each Ash resource in a domain or API, including list views (tables of records), detail views (showing a single record's fields), and forms for creating or editing records. The AshAdmin dashboard organizes resources by **domain** (or API) - developers mark a domain with AshAdmin.Domain and show? true to include all its resources in the admin[hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html#:~:text=Add%20the%20AshAdmin,4%20for%20more%20configuration%20options). Each resource can be further configured via the AshAdmin.Resource DSL (for example, marking a User resource as an **actor** with actor? true to enable impersonation[hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html#:~:text=,AshAdmin.Resource)). In the web UI, navigation is typically presented in a sidebar listing domains and their resources, with the main panel showing the selected page (resource list, detail, etc.). AshAdmin also includes a top navigation allowing admins to switch the "actor" (the user context for authorization) and tenant, reflecting Ash's multi-tenant and policy features. All these pages and functions of the web UI need to be replicated as closely as possible in a terminal-based interface.

**Functionality to Replicate:** Every page and feature of AshAdmin's web UI should be available in the Terminal UI. This includes: (1) a **dashboard of resources** (grouped by domain/API) for navigation; (2) **list pages** (tabular listing of records with pagination or scrolling, and the ability to sort columns or filter if supported); (3) **show pages** (read-only view of a record's details); (4) **create/edit forms** for resources (with proper input fields, validations and relationship selectors); (5) actions to **delete or run custom actions** on records (with confirmation prompts); (6) facilities for **impersonation/actor switching** and **tenant switching**. The Terminal UI should strive to use the _same data and configuration_ as the web UI - for example, showing the same default fields and respecting any AshAdmin.Resource configurations about which fields are read-only or hidden. In other words, the new TUI (Terminal User Interface) admin should **reuse AshAdmin's extensions and settings** as much as possible, differing only in presentation.

**Leveraging TermUI for a Rich Terminal Interface**

To implement the TUI, we will use the **TermUI** framework. TermUI is a direct-mode terminal UI library for Elixir that provides an Elm-style architecture for interactive apps, along with a rich set of widgets and cross-platform compatibility. _TermUI's capabilities align well with AshAdmin's needs:_ it offers a **rich widget library** (including tables, menus, dialogs, forms, etc.) and supports full keyboard input, mouse interactions, and flexible layouts[github.com](https://github.com/pcharbon70/term_ui#:~:text=Gauge%20Progress%20bar%20with%20color,confirmations%20with%20standard%20button%20configurations). TermUI is designed to work on Linux, macOS, and Windows terminals (Windows 10+), ensuring our admin TUI will run consistently across platforms[github.com](https://github.com/pcharbon70/term_ui#:~:text=%2A%20Cross,fault%20tolerance%2C%20hot%20code%20reload). It uses an Elm-like init/update/view architecture for predictable state management and differential rendering for performance[hexdocs.pm](https://hexdocs.pm/term_ui/01-overview.html#:~:text=What%20is%20TermUI%3F)[hexdocs.pm](https://hexdocs.pm/term_ui/01-overview.html#:~:text=%2A%20Full%20Input%20Support%20,FPS%20with%20minimal%20terminal%20updates). In practice, we can structure our TUI application as a hierarchy of TermUI components (or a single component with internal state) that represent the current "page" of the admin UI. The TermUI framework will handle low-level terminal control (raw mode, alternate screen, etc.) and allow us to focus on building interface components analogous to the AshAdmin's web components.

**Key TermUI Widgets for the Admin UI:** We will utilize TermUI's widgets to mirror AshAdmin's UI elements:

- **Menu/Tree for Navigation:** TermUI provides a hierarchical **Menu** widget that can display nested menus with submenus[github.com](https://github.com/pcharbon70/term_ui#:~:text=Gauge%20Progress%20bar%20with%20color,confirmations%20with%20standard%20button%20configurations). We can use this to create a left-hand sidebar listing each domain and its resources (the domain would be a non-selectable heading, and its resources as submenu items). The menu will allow using arrow keys or shortcuts to navigate and select a resource. Alternatively, a **TreeView** could represent nested resources, but Menu is likely sufficient. We will place this menu in a **SplitPane** layout (TermUI supports resizable multi-pane layouts[github.com](https://github.com/pcharbon70/term_ui#:~:text=SplitPane%20Resizable%20multi,command%20discovery%20with%20fuzzy%20search)) - the left pane for the resource menu and the right pane for content. This mimics the web UI's sidebar + main content layout and follows standard TUI design (similar to text-based file managers or IDEs).
- **Table for List Pages:** For listing records of a resource, we will use TermUI's **Table** widget. TermUI's Table supports a scrollable data table with selection and even sorting capabilities[github.com](https://github.com/pcharbon70/term_ui#:~:text=Gauge%20Progress%20bar%20with%20color,confirmations%20with%20standard%20button%20configurations). The table will display rows of records and columns for each field (much like AshAdmin's datatable). We can populate the table columns based on the resource's attributes; by default AshAdmin shows all fields in list view[github.com](https://github.com/ash-project/ash_admin/blob/main/documentation/dsls/DSL-AshAdmin.Resource.md#:~:text=Datatable%20pages%20format%20all%20given,DateTime%20%2C%20Ash), but if the AshAdmin DSL allows specifying visible columns, we will honor that. Users can scroll through the list (with arrow keys, page up/down) and press _Enter_ (or a dedicated key) to view the selected record's details. If TermUI's table supports column sorting out of the box, we can map a key (say s or arrow keys on header) to sort by the highlighted column, giving a similar experience to clicking column headers in a GUI (AshAdmin web might not have sorting yet, but adding it in TUI would be a nice enhancement using TermUI's capabilities).
- **Record Detail View:** When a user selects a record from the list, the TUI should show its **details (show page)**. This could either replace the table in the right pane or open in a sub-page. One approach is to implement a simple detail view as a list of field names and values (perhaps using another **Table** or just formatted text). For example, we can create a two-column table where the first column is field names and second is the value, or use TermUI's **Viewport** (scrollable content) with text lines. Read-only fields like dates or timestamps can be formatted nicely (AshAdmin's show page formats date/time fields for display[github.com](https://github.com/ash-project/ash_admin/blob/main/documentation/dsls/DSL-AshAdmin.Resource.md#:~:text=Datatable%20pages%20format%20all%20given,DateTime%20%2C%20Ash), so we'd do likewise). If the resource has relationships, we can display the related record's identifier or name; it would be useful to allow navigation into related records - e.g., highlighting a foreign key and pressing Enter to jump to that resource's show page. This could be achieved by capturing input when a relationship field is focused and then pushing a new state for that resource. We can also use a **Tabs** widget or simply separate modes to let the admin switch between "List" and "Detail" view for a resource.
- **Create & Edit Forms:** The Terminal UI must provide forms for creating new records and editing existing ones. We can leverage TermUI's **FormBuilder** widget, which supports structured forms with various field types and validation[github.com](https://github.com/pcharbon70/term_ui#:~:text=Toast%20Auto,validation%20and%20multiple%20field%20types). Using FormBuilder (or a combination of **TextInput** fields and a form layout), we can dynamically generate form fields based on the resource's attributes (and relationships). For each attribute, choose an appropriate input: text inputs for strings, number inputs for integers, etc., and for boolean or enum fields maybe a selectable menu or checkbox. Importantly, for foreign key associations (e.g. choosing a related User or Category), we can incorporate TermUI's **PickList** widget - a modal list with type-ahead filtering[github.com](https://github.com/pcharbon70/term_ui#:~:text=TextInput%20Single,style%20interfaces). This would allow the admin to search and select an associated record (similar to AshAdmin's typeahead select for relationships, which was introduced to help manage relationships[open.substack.com](https://open.substack.com/pub/ashweekly/p/ash-weekly-issue-6#:~:text=Ash%20Weekly%3A%20Issue%20%236%20,for%20reading%20Ash%20Weekly)). Validation feedback can be shown inline (the FormBuilder can validate required fields, etc.) or via messages if an error occurs on submit. When the user submits the form (e.g., by pressing a key like F5 or a labeled "Save" button in the UI), the TUI will call the underlying Ash action (create or update) and then either refresh the list or show the updated record. If the operation fails (violating validations or policies), the error message should be displayed, perhaps using a **Toast** notification or an **AlertDialog**.
- **Deleting Records & Confirmations:** Deletion or any destructive action should prompt the user to confirm. We can use TermUI's **Dialog/AlertDialog** widgets for this purpose. For instance, if the admin presses D (Delete) on a selected record, we show an AlertDialog ("Are you sure you want to delete this \[Resource\]?" with Yes/No buttons)[github.com](https://github.com/pcharbon70/term_ui#:~:text=PickList%20Modal%20selection%20with%20type,validation%20and%20multiple%20field%20types). The admin can confirm or cancel with keyboard. If confirmed, we call the Ash destroy action for that resource. After deletion, the list view should refresh (and possibly show a toast like "Record deleted"). TermUI's **Toast** widget (for transient notifications) can be used to display success or error messages in a non-intrusive way[github.com](https://github.com/pcharbon70/term_ui#:~:text=PickList%20Modal%20selection%20with%20type,validation%20and%20multiple%20field%20types) (e.g., "User created successfully" or "Error: Unauthorized" popping up briefly).
- **Custom Actions:** Ash resources may have **generic actions** (custom actions outside of standard CRUD). The TUI should surface these as well. If a resource has any generic actions defined, we can provide a way to invoke them. For example, there could be a menu or key binding for "Actions" when viewing a record or on the list screen. Pressing that could open a context menu (**ContextMenu** widget[github.com](https://github.com/pcharbon70/term_ui#:~:text=PickList%20Modal%20selection%20with%20type,Hierarchical%20data%20display%20with%20expand%2Fcollapse)) listing available actions for the selected resource. Selecting an action might open a form (if the action requires input arguments) or immediately execute it if none required. We will reuse Ash's definitions of these actions (accessible via the Ash resource's API or introspection) to present prompts for required input and then call the action. This ensures even non-CRUD functionality present in AshAdmin is available in the TUI.

**UI Design and Navigation in the Terminal**

Designing a TUI that is intuitive requires thoughtful layout and navigation cues, since we lack the mouse-driven ease of a GUI. We will follow standard TUI design patterns to ensure usability:

- **Layout:** The interface will be divided into sections much like a GUI. A common pattern (also seen in TermUI's dashboard example) is a top bar, a left sidebar, a main content area, and a bottom status bar. We will likely implement a **top bar** that displays the application title and context (e.g., "AshAdmin TUI - \[Current User/Actor: AdminUser\] \[Tenant: default\]"). The **sidebar** (left pane) lists domains and resources (as discussed, using a Menu). The **main content** (right pane) shows whatever page is active (list, detail, form, etc.). We can also use a bottom line as a **status or help bar**, showing key hints. For example, we might show something like: \[←/→\] Switch Pane \[↑/↓\] Navigate \[Enter\] Select \[A\] Actions \[E\] Edit \[N\] New \[D\] Delete \[Q\] Quit. This provides users a quick reference to available keys, which is crucial for usability. TermUI allows us to capture key events globally, so pressing Q can quit, N can open the new-form, etc. The bottom bar (or occasional popup help dialog) will ensure the user knows how to interact, reducing the learning curve.
- **Navigation & Focus:** We will implement keyboard navigation such that the user can switch focus between the sidebar and the main content. Perhaps pressing Tab or a specific key can move focus. When the sidebar (resource menu) is focused, up/down keys move through resources; hitting Enter on one will load that resource's list page in the main pane. When the main content (like a list) is focused, up/down scrolls the table, etc. TermUI handles focus and even mouse events, so if a user clicks (in a mouse-enabled terminal) on the menu, it could focus/select - but keyboard will be primary. Consistent visual cues will be provided: the selected menu item or table row will be highlighted (TermUI supports styles like inverse or color for selection). We will choose a color theme (TermUI supports theming with 16+ colors[hexdocs.pm](https://hexdocs.pm/term_ui/01-overview.html#:~:text=%2A%20Rich%20Widget%20Library%20,FPS%20with%20minimal%20terminal%20updates)[hexdocs.pm](https://hexdocs.pm/term_ui/01-overview.html#:~:text=Rich%20styling%20with%20colors%20and,attributes)) that ensures good contrast and a familiar feel (for instance, blue or yellow highlights as seen in TermUI's demo images, to give it a classic ncurses UI vibe). The design will be responsive to terminal size - TermUI's constraint-based layouts[hexdocs.pm](https://hexdocs.pm/term_ui/01-overview.html#:~:text=Declarative%20constraints%20for%20flexible%20layouts%3A) allow components to resize. For example, the sidebar can have a fixed width or percentage, and the table can fill the remaining space.
- **Standard UI Elements:** The TUI should mirror graphical UI conventions in text form. For example, dialog boxes for confirmation or input will center on screen and draw a box with borders (TermUI likely has built-in styling for Dialog). Menus and pop-ups should be bordered or highlighted distinctly. We will also handle long text gracefully: e.g., if a field's value is very long, the detail view might wrap it or allow horizontal scrolling. TermUI's **Viewport** or just text wrapping can manage this. The goal is to prevent the interface from breaking on various content lengths and terminal sizes.
- **Error Handling & Feedback:** In a web UI, errors or successes might be shown as flash messages or inline form errors. In the TUI, we will use a combination of the bottom status bar for ephemeral messages and pop-up dialogs for more persistent alerts. For instance, if an operation fails due to a policy (authorization) denial, the TUI could display a red-highlighted message in the status bar ("Access Denied: You do not have permission") and wait for the user to press a key to acknowledge if needed. Alternatively, a modal AlertDialog can show the error with an "OK" button. Success messages could be shown as subtle toasts that disappear. Providing clear feedback is essential so the user knows an action happened. We will also log any unexpected errors to console or a log file, since a TUI might be used by developers/admins who may watch logs.
- **Cross-Platform Considerations:** Thanks to TermUI's design, we don't have to implement different UIs per OS - it abstracts differences in how terminals work. The main consideration is ensuring keys we choose are available on all platforms (for example, the Alt key sequences might not work uniformly, so we'll stick to basic keys, function keys, or single letters). Also, TermUI uses an alternate screen buffer by default (as indicated in its docs), so when our TUI app exits, it will restore the original terminal content - this is good practice so we don't clutter the user's shell. We should test the interface on Windows Terminal, macOS Terminal, and common Linux terminals to ensure rendering (box drawing characters, colors) appear as expected. By using TermUI's provided widgets and not raw control codes ourselves, we inherit its cross-platform reliability[github.com](https://github.com/pcharbon70/term_ui#:~:text=%2A%20Cross,fault%20tolerance%2C%20hot%20code%20reload).

**Integrating with Ash Framework Back-end**

The TUI will not exist in isolation - it needs to interact with the Ash application (the server). To maintain parity with AshAdmin, we should integrate using the same **Ash extensions and authentication mechanisms**:

- **Using AshAdmin's Configurations:** Rather than duplicating configuration, the terminal UI can depend on the AshAdmin (and Ash framework) libraries to retrieve information about resources. For example, AshAdmin's DSL adds metadata to each resource (like which fields are shown in tables or forms, which actions to include, etc.). Our TUI code can query the resource's configured attributes and relationships via Ash's reflection functions or even via AshAdmin's internal APIs if available. The goal is that if a developer configures a resource for AshAdmin (say they hide a sensitive field from the admin UI), the TUI automatically respects that. We will use the same AshAdmin.Domain markers to decide which resources to show in the menu (e.g., filter to domains with show? true[hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html#:~:text=Add%20the%20AshAdmin,4%20for%20more%20configuration%20options)). Likewise, identify the actor resource via actor? true[hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html#:~:text=,AshAdmin.Resource) to know which resource represents users for impersonation. All the heavy lifting of listing resources, getting their primary keys and so on can be done through Ash itself (for instance, using Ash.Api or Ash.Query to fetch records for the table). This means our TUI is essentially another **client** of the Ash APIs, just like the Phoenix LiveView in AshAdmin - we call the same Ash actions (read, create, update, destroy) under the hood. By depending on the Ash and AshAdmin libraries, we also ensure future changes (like new field types or validations) are handled consistently.
- **Authentication via AshAuthentication:** The web AshAdmin typically relies on the hosting Phoenix app to secure the /admin route (for example, requiring a user login and perhaps an admin role)[preview.hex.pm](https://preview.hex.pm/preview/ash_admin/0.9.3/show/README.md#:~:text=,prevent%20them%20from%20being%20public)[hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html#:~:text=scope%20%22%2F%22%20do%20,browser). In our terminal scenario, we need an equivalent authentication and authorization mechanism. The TUI will **use AshAuthentication**, the same library used in the Ash ecosystem for user auth. The strategy should match the server's setup. For instance, if the server uses an email/password login with AshAuthentication, the TUI will prompt the admin for their credentials on startup. The credentials can be verified by calling the server's authentication logic. There are a few ways to do this:
  - _If the TUI runs as a separate client:_ We might have the server expose a sign-in API (HTTP or RPC). AshAuthentication's Phoenix integration can provide token endpoints (e.g., a JWT issuance on login). The TUI could collect username/password, send them to the server's auth endpoint, and receive a token if valid. This token (JWT) would then be attached to subsequent requests from the TUI when calling protected APIs. Using a token-based approach aligns well if the server has JSON API or GraphQL endpoints for Ash resources - the TUI could be essentially calling those. We will ensure to use AshAuthentication's mechanisms (e.g., AshAuthentication.Jwt for token generation[hexdocs.pm](https://hexdocs.pm/ash_authentication/AshAuthentication.Jwt.html#:~:text=Uses%20the%20excellent%20joken%20hex,order%20to%20generate%20and)) so that we're not inventing a new auth method.
  - _If the TUI is running in the same BEAM instance or connected via distribution:_ In this case, the TUI could directly call AshAuthentication to verify credentials (for example, calling AshAuthentication.Strategy.Password.sign_in(username, password) or similar if provided). It could then set the current actor (there might be an Ash API to set actor context on a per-call basis, or we pass the actor explicitly into Ash queries and changesets). When integrated in the same app, the TUI would essentially bypass Phoenix but still rely on AshAuthentication's user storage and hashing to authenticate.

In either scenario, **the same policies and roles apply**. In AshAdmin (web), one common approach is to restrict admin access by user role (e.g., only allow users with :admin role to use the admin)[hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html#:~:text=Then%2C%20we%27ll%20need%20to%20define,example_web%2Flive_user_auth.ex). We will mirror that: after login, if the user does not have the appropriate role, the TUI will refuse access (display an error and exit or re-prompt). If the user is authorized, we proceed into the admin interface.

- **Maintaining Session/Actor:** Once authenticated, the TUI needs to operate under the identity of that user for authorization. Ash's policy engine uses the "actor" (usually the current user) to permit or forbid actions. In a Phoenix app, this is often handled by setting assigns\[:current_user\] and using Ash.Plug or contexts. In our TUI, we will maintain an in-memory reference to the logged-in user (and possibly their token if using external API calls). Every call to Ash (or every API request) will include this identity. For example, if calling Ash queries directly, we can use Ash.Query.for_read(action, params, actor: current_user) so that Ash policies see the actor. If calling an HTTP API, include the JWT in the Authorization header so the server knows who the actor is. This way, all authorization **policies** defined in the Ash resources will consistently apply to operations from the TUI. (Notably, AshAdmin by default does not add extra authorization beyond Ash policies - it warns that it has no built-in security aside from those policies[preview.hex.pm](https://preview.hex.pm/preview/ash_admin/0.9.3/show/README.md#:~:text=,prevent%20them%20from%20being%20public). This implies that as long as we honor the same actor and policies, the TUI will enforce permissions in the same way).
- **Actor Switching (Impersonation):** A powerful feature of AshAdmin is the ability to switch the actor context - e.g., an admin can choose to "act as" a regular user to see what they would see. In the web UI, this is done by marking a resource as actor? true and using an actor dropdown or a "key" icon on user records to assume that identity[answeroverflow.com](https://www.answeroverflow.com/m/1446508994586738828#:~:text=You%20can%20designate%20some%20resources,as%20%20resources). We will implement this in the TUI as well. Since we know which resource is the actor resource (user), we can provide a command (say I for impersonate or a menu item) to select an actor. For instance, the admin could press a key and get a **PickList** of users (with search) to choose from. Once selected, the TUI will set that as the current actor for policy checks in read actions (and perhaps indicate it in the top bar, e.g., "Actor: Jane Doe"). This "impersonation" should be done carefully - likely we do not re-authenticate as that user, we simply use their identity for Ash's authorization context. (AshAdmin still requires the admin to be logged in as themselves, but lets the interface run queries as if another user were the actor[answeroverflow.com](https://www.answeroverflow.com/m/1446508994586738828#:~:text=You%20can%20designate%20some%20resources,as%20%20resources).) We'll ensure a clear way to "exit" impersonation (maybe pressing a key to revert to admin or selecting a menu option "Return to admin context"). This feature is crucial for testing policies and viewing data scoped to different users, just as in the web AshAdmin.
- **Multi-Tenancy Support:** Ash supports multi-tenancy, and AshAdmin UI allows switching the tenant (often via a dropdown in the top nav). Our TUI will include a similar control. Possibly the top bar or a menu command to "Change tenant" that opens a small dialog to input the tenant name (or choose from a list if known). We will then use that tenant for all subsequent Ash calls (Ash APIs often accept a tenant option or you set the Ash.Query.set_tenant/2). TermUI's **Form or TextInput** can be used to prompt for tenant if needed. As TermUI is cross-platform and handles text input, there's no issue handling arbitrary tenant strings. The current tenant should be displayed alongside the actor in the UI for clarity.
- **Dependency Management:** Our new TUI project will be an Elixir application that depends on the Ash framework, AshAdmin (for the DSL/config) and AshAuthentication (for auth), as well as TermUI for the interface. The idea is to reuse as much logic as possible. For example, if AshAdmin has internal modules for things like formatting a resource's data (dates, etc.), we could call those or mimic them. The TUI app itself can be started as a standalone escript or mix task (mix ash_admin.tui) that brings up the interface after prompting for credentials. It might connect to the running server via configured API endpoints. If the server and TUI are part of the same umbrella or release, one could even start the TUI from a remote IEx session connected to the server - but the simplest approach is a separate client program using HTTP API. In any case, the **authorization and authentication strategy remains identical** to the web: login with AshAuthentication, enforce roles/policies, and use the Ash context for allowed operations.

**Summary and Recommendations**

In summary, the design for a Terminal UI version of AshAdmin will preserve all functionality of the web dashboard while providing a clean, text-based user experience. We will use **TermUI** to create a robust interface, complete with a navigation sidebar, data tables, forms, dialogs, and more, closely mirroring AshAdmin's pages. By leveraging AshAdmin's existing extensions and the Ash framework's introspection, the TUI will automatically include all configured resources and honor field and action configurations, differing only in presentation (terminal-friendly output instead of HTML). Authentication and authorization will be handled by **AshAuthentication**, just as in the web version - administrators must log in through the same strategies (e.g., password login, receiving a JWT or session) and only authorized users (e.g., those with an admin role) can access the TUI[hexdocs.pm](https://hexdocs.pm/ash_admin/getting-started-with-ash-admin.html#:~:text=scope%20%22%2F%22%20do%20,browser). TermUI's cross-platform nature ensures the admin interface works on any OS without special adjustments[github.com](https://github.com/pcharbon70/term_ui#:~:text=%2A%20Cross,fault%20tolerance%2C%20hot%20code%20reload), making it a viable tool for developers and ops teams working remotely or over SSH.

Designing the TUI with standard UI/UX principles - clear navigation, keyboard shortcuts, visual feedback on selection, confirmation prompts - will result in an interface that feels familiar to anyone who has used text UIs like htop or mc. The AshAdmin Terminal UI will empower users to manage Ash resources from a terminal with (almost) the same ease as the web GUI, using the full power of Ash's data layer under the hood. By keeping the implementation consistent with AshAdmin's architecture and using TermUI's rich components, we ensure feature parity and a maintainable codebase. The end result will be a **fully-functional AshAdmin TUI** that supports all CRUD operations, custom actions, impersonation, and multi-tenancy, all secured by Ash's authentication and authorization framework - just in a lightweight, terminal-based form.
